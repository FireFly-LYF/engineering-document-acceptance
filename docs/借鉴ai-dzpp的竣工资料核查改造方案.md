# 借鉴 ai-dzpp 的竣工资料核查改造方案

日期：2026-10-09。对照目录：`D:\桌面\work\ai-dzpp` 与本项目。

## 1. 判断与建议

建议保留当前“AGH + 核查 Skill + 文书 Skill”的使用入口，逐步把核查脚本升级为具有统一解析、证据来源、工程领域规则和回归验证的本地核心。ai-dzpp 提供文件理解与证据处理的参考实现；竣工资料齐套、适用性、项目归属和内容一致性应由新的工程领域规则决定。

旧方案解决出口单证归属匹配：以报关单参考值为线索，抽取文件候选值，再寻找可满足配置规则的组合。当前方案解决工程资料核查：既要确认文件属于本项目，也要确认资料类型、阶段、覆盖范围及异常。两者共享解析和候选表示，但通过标准不同。工程文件具有相同项目编号，并不意味着材料齐套或内容无冲突。

本次进行文件与代码审阅，没有调用旧项目业务模型、读取其 `.env` 密钥、修改旧项目，或宣称其完整测试已经通过。下文区分已有实现和建议实现。

## 2. 已确认的旧项目能力及边界

| 层次 | 本地实现位置 | 可借鉴内容 | 迁移限制 |
|---|---|---|---|
| 文件接收 | `app/io/file_scanner.py` | 多格式识别、部分魔数识别、临时文件扩展名处理 | 新项目需递归处理阶段目录，并稳定分配 file_id；不能仅用 basename 作键 |
| 原生解析 | `app/native/extractor.py` | PDF 全文及坐标、DOCX、Excel 各工作表、表格结构 | 必须按具体格式验证能力，不能仅凭扩展名识别宣称读取成功 |
| OCR | `app/preprocessing/page_preparer.py`、`app/ocr/` | 页图准备、结构化 blocks、表格及来源 | OCR 接口与供应商相关，应通过适配器隔离 |
| 阅读表示 | `app/document/markdown_units.py` | MarkdownUnit、SourceFragment、页码、bbox、表格行列来源 | Word/Excel 使用逻辑单元，不能编造物理页码 |
| 字段定义 | `app/fields/field_registry.py`、`field_definitions.yaml` | 字段含义、别名、类型、约束配置 | 删除报关单字段、买卖方角色及外贸枚举，替换为工程字段与角色 |
| 锚值搜索 | `app/fields/declaration_search.py` | exact/normalized_exact/substring、候选来源、锁定机制 | 工程核查不能因找到锚值就停止发现异常值 |
| 候选提取 | `app/llm/markdown_field_extractor.py` | 候选列表、原文定位、按页工作池、类型检查 | confidence 是排序信息，不是事实正确率；必须记录拒绝与失败原因 |
| 值比较 | `app/matching/value_matcher.py` | 日期、数值、单位及归一化比较 | 不能直接继承 OCR 字符纠正、模糊匹配或合计策略作为正式一致性标准 |
| 规则判断 | `app/matching/rule_engine.py` | 配置规则、逐条证据、候选选择记录 | “存在一致候选组合”不能替代“所有相关取值均无冲突” |
| 运行管理 | `app/usage.py`、`app/server/`、`app/storage/` | 阶段耗时、调用统计、任务状态、日志归档 | API/MySQL 延后；线程安全不等于任务统计隔离，应每次运行独立收集 |
| 验证 | `tests/`、`cases/`、`scripts/` | 模块测试、批量用例、前后结果对比 | 本地有 29 个 test_*.py、50 个一级 cases 目录；数量不代表覆盖完整或已经通过 |

### 2.1 不应按历史文档直接复制

1. 迁移文档描述全部格式进入 Markdown；当前 `ApiPipelineRunner.run_case` 将图片及检测到 OCR 来源的扫描 PDF 分到多模态字段提取路径，未统一进入 Markdown 字段提取。
2. 文档描述“每个文件一次字段请求”；当前 `extract_markdown_field_candidates` 使用 `per_unit=True` 和全局页工作池，实际调用数量受单元数影响。
3. 当前 `declaration_search` 仅对单参考值 exact/normalized_exact 命中锁定；substring 和多参考值保持候选。历史文档的“所有命中锁定”已不准确。
4. 新版 README 和代码使用 1/2/4 三种业务状态，历史迁移文档描述 1/2/3/4。当前归属规则可因 link evidence 共识给出建议通过，工程核查不能继承该升级作为齐套或一致性通过。
5. `concurrency.py` 中模型并发上限为 500/400，线程池还有余量。新项目应从保守可配置值开始，按实际吞吐调整，不能照搬。
6. PDF 原生提取会跳过无文本页，而摄入 OCR 主要在整份文件没有 native_pages 时触发。混合文本/扫描 PDF 可能漏识别扫描页，应改成逐页路由。
7. 旧项目 Markdown 候选路径有原文 grounding；图片多模态路径主要做结构类型验证，其 evidence 不能直接视为已由原文验证。工程核查应补 OCR 对齐或明确视觉证据的审核状态。

## 3. 当前项目需要先解决的问题

### 3.1 清单匹配缺少通过门槛

`match_required` 为分类一致加 1 分，任何正分都进入候选，后续可能标为 provided。已用独立最小输入复现：缺少消防验收材料时，规划核实证明仅凭 special_acceptance 同类就被当成消防项候选。

改为两步：先判文件是否满足该清单项的准入条件，再对合格候选排序。准入至少涉及具体资料类型、项目归属、阶段或范围；分类相同只帮助检索，不提供通过证据。

### 3.2 演示文件名被写进业务逻辑

`E-01`、`滨河`、`管廊`、`99-错传` 参与正式报告和错传判断。应以通用资料类型和规则中的 exclusion/substitute 配置处理预验收，按项目身份字段判归属。重命名、移出“错传”目录后，判断应保持一致。

### 3.3 解析不足和真正缺件未区分

目前读取前两页文本，保存的 text_head 又截断；图片及 Office 文件没有相应正文读取。无法识别的候选文件可能被当成不存在。

应保存每页读取状态及失败原因。仅当不存在合理候选且搜索范围充分时判 missing；有疑似材料但读不出、页未覆盖或身份未确认时判 needs_human_review。

### 3.4 归属差异与本项目冲突混在一起

当前 `build_consensus` 汇总全部文件，错传文件的单位、地址、日期等进入项目字段冲突。文书于是将两份错传引起的差异扩展为十类复核字段。

应先判归属：target_project / other_project / unresolved。other_project 进入错传证据，排除出本项目一致性统计；unresolved 单独复核，不静默并入。目标项目内部继续比较编号、金额和其他同语义字段。

### 3.5 Skill 说明和脚本行为尚未完全一致

Skill 描述从 manifest 选择规则、多格式处理、日期等核查；脚本默认规则固定为 housing-construction，部分描述能力尚未实现。每一项应有实现、降级或明确未覆盖说明。道路桥梁、市政管线清单标记为 draft，不能输出完整齐套结论。

## 4. 建议的数据流

```text
manifest + 工程规则 + 原文件
  → 文件登记、哈希、页数、格式与读取状态
  → 逐页原生解析 / OCR fallback
  → 文档单元 + Markdown + source map
  → 工程资料类型及阶段识别
  → 工程字段候选 + 原文定位 + 类型/单位校验
  → 项目归属判断（保留编号等异常）
  → 清单准入、齐套、覆盖范围及适用性核查
  → 本项目字段一致性、日期关系、重复/版本核查
  → findings + review_queue + 统计 + 证据链
  → 文书 prepare → Agent 正文 → 正文校验 → Word build → 版面检查
```

文件解析可全量执行，Agent 仍只阅读 brief 和必要证据页。这里“脚本全量提取”和“Agent 不通读所有 PDF”并不矛盾。

## 5. 字段与证据模型

字段定义至少包括 field_id、语义、数据类型、别名、单位、适用文档类型、比较策略。合同金额、结算金额、投资总额分别定义；开工日期、合同签署日期、验收日期分别定义。单位名称按建设、施工、监理、设计角色分别提取，不能把同页任意公司名称互相填入。

建议候选结构：

```json
{
  "candidate_id": "file_012:p3:contract_amount:1",
  "field_id": "contract_amount",
  "raw_value": "9200万元",
  "normalized_value": "92000000",
  "unit": "CNY",
  "source_label": "施工合同金额",
  "file_id": "file_012",
  "page_no": 3,
  "fragment_ids": ["p3_block_17"],
  "evidence_text": "施工合同金额：9200万元",
  "extraction_source": "native_rule",
  "grounding_status": "verified",
  "confidence": 0.95,
  "value_role": "contract_total"
}
```

金额使用 Decimal 与明确单位转换，保留原值和转换过程。编号只做许可的格式归一化；018/019 不能模糊通过。OCR 字符纠正只能给出疑似等价候选及复核建议。日期解析失败须给出证据不足，不继续按普通数字比较。

每个 finding 有稳定 id、rule_id/version、status、reason_code、严重度、正负证据 id、处理建议和判定覆盖范围。Agent 修正记录保存旧值、新值、理由和证据，最终文书只消费确认后的核查结果。

## 6. 从旧方案迁移时必须改变的判断方式

### 6.1 锚值用于定位，不能覆盖文档事实

manifest 优先提供期望项目身份，并记录其来源。借鉴 `declaration_search` 做证据检索，但命中只证明出现，不能证明该值属于目标字段，也不能终止异常搜索。

例如报告首页编号为 019，附件引用合同编号为 018。若搜索锚值 018 后锁定，会漏掉正文编号异常。工程提取应保留两处候选及其角色，报告主体编号 019 与 manifest 018 的冲突仍存在。

### 6.2 候选组合用于消除歧义，不能用来掩盖冲突

旧方案寻找能够满足匹配规则的候选。工程核查应先区分合同总额、调整后金额、明细和其他引用值，再比较同语义值。若两个候选都明确属于合同总额，不能只挑选其中与锚值相同的值后判通过。

候选语义不清时进入人工复核；同语义的多个取值不一致时生成冲突 finding，并保留版本和日期。如果是合法变更，用变更文件说明解释，不能静默忽略。

### 6.3 归属和内容一致性分开

编号不一致也可能是本项目笔误，不应直接移为 other_project。结合项目名、地址、建设单位等独立身份线索，保留“属于本项目但编号异常”的结果。明确属于其他工程的材料不参与齐套通过，也不污染本项目字段共识。

跨文件 link evidence 可解释归属或支撑关系，不能补出缺失消防材料、替代正式验收报告，或消除金额冲突。

### 6.4 资料类型存在与覆盖完整分开

一份检验批记录可以证明该类材料已提供，不能证明所有楼栋、楼层、分项的记录齐套。当前 24 份演示包可继续作为“资料类型级”核查；若宣称范围级完整，需要应交范围数据。

规则建议增加 document_type、required_when、min_count、coverage_scope、accepted_substitutes、exclusions、rules_version、region、effective_date、source_reference。属性未知时明确未判定，不自动当作不适用或缺失。

签字盖章、竣工图变更覆盖、检测报告与部位关联均应记录实际覆盖；有文本签署栏不等于存在真实签名或有效印章，标题页不等于图纸齐全。

### 6.5 重复与版本分开

依次使用文件 SHA-256、文本指纹、文件编号+类型+项目身份判断。完全一致判重复；同编号不同内容、不同日期或不同签章判版本冲突/待确认。编号相同不能直接删除文件。

## 7. 模块组织与复用方式

建议把通用能力放入项目级 Python 包，Skill 脚本作为薄入口：

```text
app/
  models.py
  ingestion/       # 登记、逐页解析、source map
  extraction/      # 字段候选、类型校验、grounding
  audit/           # identity/checklist/consistency/duplicate
  reporting/      # findings/brief/事实校验
  providers/      # 可选 OCR/模型适配器
rules/
tests/
.agh/skills/engineering-archive-audit/scripts/audit_prepare.py
.agh/skills/engineering-doc-generator/scripts/generate.js
```

第一阶段在当前核查脚本修复错误并增加测试；接口稳定后再拆分模块，避免重构和判断规则同时大改。

首版更适合有选择地移植旧代码及相关测试，并把 `app.*` 导入改成新项目命名空间，不建议通过 sys.path 直接引用旁边的 ai-dzpp。这样可以独立部署、冻结行为，也不会把外贸配置、API 和业务依赖一起拖入。

如果以后确实有多个业务项目共享解析层，再抽成独立版本的公共包。新项目的工程规则和文书逻辑仍独立。

## 8. 保留当前模型与 Skill 使用方式

当前 README 指定 AGH/Agnes、不依赖第三方业务模型 API。默认迁移继续保留该约定，复用数据结构和验证逻辑，而非自动继承 DashScope。

先让本地解析和显式规则处理可确定内容。语义不明确的字段生成有页码和片段的提取任务，由 AGH 中的 Agent 返回结构化候选，再由脚本校验；Agent 不直接改 findings 去绕过证据。现有 Skill 需相应增加提取/复核任务协议，保留“脚本先行、避免通读”的要求。

扫描件先通过可配置 OCR 适配器形成文本和坐标；未配置或读取失败时降级为 needs_human_review。若未来选择外部 OCR/LLM，通过独立配置启用、逐项记录调用与证据，不作为基础流程的必需依赖。

## 9. 对接文书生成

继续保留 prepare → Agent 正文 → build，但在 build 前增加事实校验。

1. 接收文件数量来源于实际 inventory，不优先使用可能过期的 manifest.file_count。
2. 文件份数、清单条目数、冲突字段数、重复组数分别统计，不能加在一起作为文件数。
3. 主项目字段冲突与错传导致的差异分开陈述。
4. 正文中的项目、编号、金额、数量和关键结论必须关联 facts/finding。对不能自动可靠解析的自由文本断言给出人工校对提示，不声称仅凭正则实现全部事实验证。
5. 缺失但存在未识别候选时，正文应保留证据不足的限定；不能写成确定未提交。
6. 把“问题资料清单”与“实际附件”分开；缺失资料不能列为已经随文附上的附件。
7. Markdown 解析应支持实际使用的加粗、有序列表，避免 `**` 原样输出、编号合段；随后做 Word/PDF 页面检查。
8. 保存最终 findings、facts、正文、文书、证据索引及规则版本，支持追溯。

## 10. 实施顺序与完成标准

### 阶段 A：先让现有演示结果正确

修改核查脚本、housing 规则和规则选择；修复分类冒充类型、消防误判、硬编码错传、身份统计污染；修正文书数量、附件与 Markdown 排版。

验收：现有演示包稳定识别正式验收与消防缺失、两份错传、目标项目编号与金额异常、一组重复；错误文件重命名后仍正确；规则条目重编号不破坏正式/预验收关系判断。

### 阶段 B：建立可追溯解析与字段候选

迁移原生解析、页模型、Markdown/source map 的必要模块；补逐页 OCR 路由、递归 file_id、失败状态；增加工程字段配置。

验收：第三页字段可定位；文本+扫描混合 PDF 不漏页；两份同名不同路径文件不互相覆盖；XLSX 第二工作表可读取；无证据候选不能进入确认结果；无法读取不被静默判缺失。

### 阶段 C：建立工程领域规则

分离身份、清单、覆盖范围、一致性、日期、重复/版本；扩展规则元数据和条件适用性；增加人工复核闭环。

验收：锚值在附件出现仍能发现正文冲突；一份检验批不被写成全范围齐套；错传不计入主项目共识；金额单位转换正确；同编号不同内容进入版本复核；缺少范围数据时限定结论。

### 阶段 D：稳定文书和运行产物

保留 Skill 两段式流程，增加正文事实核对、渲染抽查、按 run_id 存档、输入/规则指纹、阶段耗时和可选模型用量。

验收：统计可从 findings 重算、编号金额与证据一致、Markdown 标记不泄露、列表不合段；同一输入与规则的确定性阶段保持一致；输入或规则变化后不复用陈旧结果。

### 阶段 E：按使用规模服务化

只有出现多用户并发、上传、查询与长期任务管理需求时，再借鉴 FastAPI、worker、TaskStore 与 MySQL。API 输出须保留 candidate、finding、evidence 字段，防止服务响应模型丢弃本地核查元数据。

## 11. 最小回归用例

| 用例 | 必须得到的行为 |
|---|---|
| 只有规划核实、没有消防 | 消防 missing，规划不能替代 |
| 只有预验收 | 正式验收 missing，保留 similar evidence |
| 错传移出原目录并改文件名 | 根据项目身份仍识别 other_project |
| 同项目报告编号单字符异常 | 本项目字段冲突，不自动排除该报告 |
| 附件锚值正确、正文编号错误 | 正文异常仍被报告 |
| 正文同时存在同语义两种金额 | 冲突或复核，不能选一个值后通过 |
| 合同金额与结算金额不同 | 先区分语义，不直接判冲突 |
| 8650 万元与 86500000 元 | 转换后相等，保留转换证据 |
| 第三页有字段 | 提取且保留物理页码 |
| 混合文本/扫描 PDF | 逐页补 OCR 或明确未覆盖页 |
| 损坏 PDF / OCR 失败 | 记录失败，不能直接等同缺件 |
| 同编号不同正文 | 版本冲突或复核，不自动去重 |
| 完全相同 PDF 两份 | 一组重复，不计成两个重复问题 |
| 两阶段目录同名 PDF | file_id、字段和证据均独立 |
| 规则占位或适用条件未知 | 声明未完备/未判定，不输出全面齐套 |
| 一份检验批、应交范围未知 | 仅证明类型已提供，不宣称范围齐套 |
| 幻觉值或错误页码候选 | 拒绝，保留拒绝原因 |
| 文书数量与 findings 不同 | 阻止直接发布或提示明确待校对 |

除案例数量外，持续统计：清单误判率、错传/冲突/重复检出、未识别与复核比例、证据覆盖率、各阶段耗时及调用用量。合成演示通过后再使用经授权的不同版式材料做验证，不能据一个案例宣称真实项目可用。

## 12. 建议优先落实的范围

首轮范围：现有核查错误修复 + 统一原生解析 + 来源证据 + 归属与冲突分离 + 文书校对 + 上述关键回归用例。扫描件适配随后补齐；范围级完整性由应交范围数据决定；API 和数据库后置。

这条路径保留当前两套 Skill 的轻量入口，同时吸收旧项目可追溯候选和运行验证的做法，把工程核查的通过标准建立在明确规则与可检查证据上。
