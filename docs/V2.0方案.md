# 工程竣工资料智能核查方案 V2.0

## 1. 目标

V2.0 面向建设工程竣工资料的完整性、归属和一致性核查。用户新建任务时只需选择工程类型并填写项目名称，上传资料后由系统根据工程类型规则自动选择主参考文件，生成结构化 `manifest.json`，再对全部资料逐页提取字段并执行核查。

系统输出机器可读的核查结果、字段证据链和前端可展示的逐文件结果。AGH/Agent 负责读取 Skill、调用确定性工具、复核疑点和整理报告；字段类型校验、归一化、规则判断和状态计算由规则引擎完成。

## 2. 用户流程

```text
新建核查任务
  ↓
选择项目类型（必选）+ 填写项目名称（必填）
  ↓
上传工程资料
  ↓
加载对应工程规则
  ↓
自动选择主参考文件
  ↓
从主参考文件生成 manifest.json
  ↓
全部文件逐页提取字段和证据
  ↓
执行字段范围、字段一致性和字段关系规则
  ↓
执行材料完整性、项目归属和重复文件核查
  ↓
返回前端结果并生成核查报告
```

## 3. 任务创建

用户必须填写两个字段：

- `project_type`：工程类型
- `project_name`：项目名称

当前类型包括：

| 类型 | 规则文件 | 状态 |
|---|---|---|
| 房屋建筑工程 | `housing-construction.json` | 规则较完整，可用于正式演示 |
| 道路/桥梁工程 | `road-bridge.json` | 占位规则 |
| 市政管线工程 | `municipal-pipeline.json` | 占位规则 |

任务配置只保存用户输入和任务身份，不预先填写施工单位、合同金额、日期等核查答案：

```json
{
  "project_id": "task-001",
  "project_type": "housing-construction",
  "project_name": "云港新区市民活动中心图书馆工程",
  "rules_profile": "housing-construction",
  "created_at": "2026-10-12T09:00:00+08:00"
}
```

## 4. 规则文件结构

每种工程类型由一个规则文件描述。规则文件维护四类内容：

```text
manifest_fields       要维护和提取的结构化字段
primary_reference     主参考文件定义
required_documents    必需资料清单
consistency_rules     字段核查规则
```

### 4.1 manifest 字段表

```json
{
  "manifest_fields": [
    {
      "key": "project_name",
      "name": "项目名称",
      "type": "text",
      "required": true,
      "aliases": ["工程名称", "建设项目名称"]
    },
    {
      "key": "project_code",
      "name": "项目编号",
      "type": "identifier",
      "required": true,
      "aliases": ["工程编号", "建设项目编号"]
    },
    {
      "key": "owner",
      "name": "建设单位",
      "type": "organization",
      "required": true
    },
    {
      "key": "contractor",
      "name": "施工单位",
      "type": "organization",
      "required": true
    },
    {
      "key": "supervisor",
      "name": "监理单位",
      "type": "organization",
      "required": true
    },
    {
      "key": "designer",
      "name": "设计单位",
      "type": "organization",
      "required": false
    },
    {
      "key": "address",
      "name": "工程地址",
      "type": "text",
      "required": false,
      "aliases": ["建设地点", "工程地点"]
    },
    {
      "key": "start_date",
      "name": "开工日期",
      "type": "date",
      "required": false
    },
    {
      "key": "finish_date",
      "name": "竣工日期",
      "type": "date",
      "required": false
    },
    {
      "key": "contract_amount",
      "name": "合同金额",
      "type": "money",
      "required": false,
      "aliases": ["签约合同价", "合同价格"]
    }
  ]
}
```

字段定义还可以包含正则、单位、是否可累加、日期格式、枚举值和归一化方式。

### 4.2 主参考文件

主参考文件类似出口单证核查中的报关单，是生成结构化 manifest 的数据锚点：

```json
{
  "primary_reference": {
    "code": "A-02",
    "name": "建筑工程施工许可证",
    "aliases": ["施工许可证", "开工证"]
  }
}
```

系统根据文件名、标题、分类、项目名称和可读性自动选择主参考文件。没有找到主参考文件，或存在多个无法区分的候选时，任务进入人工复核，不能直接生成正式核查结论。

### 4.3 必需资料清单

```json
{
  "required_documents": [
    {
      "code": "A-02",
      "name": "建筑工程施工许可证",
      "required": true,
      "category": "preparation",
      "aliases": ["施工许可证", "开工证"]
    },
    {
      "code": "E-01",
      "name": "工程竣工验收报告",
      "required": true,
      "category": "completion_acceptance",
      "aliases": ["竣工验收报告"],
      "notes": "预验收报告默认不能替代正式竣工验收报告"
    }
  ]
}
```

### 4.4 字段核查规则

规则文件一般维护三条核心规则：

```json
{
  "consistency_rules": [
    {
      "rule_id": "R-001",
      "name": "字段适用范围",
      "type": "field_scope",
      "scopes": [
        {
          "field": "contract_amount",
          "documents": ["施工合同", "施工单位工程竣工报告", "工程竣工验收报告"]
        },
        {
          "field": "supervisor",
          "documents": ["监理合同", "监理规划", "工程质量评估报告"]
        }
      ]
    },
    {
      "rule_id": "R-002",
      "name": "manifest 字段一致性",
      "type": "manifest_consistency",
      "operator": "all_values_equal"
    },
    {
      "rule_id": "R-003",
      "name": "无 manifest 值时的跨文件一致性",
      "type": "cross_file_consistency",
      "operator": "all_values_equal",
      "min_values": 2,
      "only_when_manifest_empty": true
    }
  ]
}
```

规则还可以增加金额、日期和编号的专门约束，例如：

- 施工合同、竣工报告和正式验收报告中的合同金额应一致
- 竣工日期必须晚于开工日期
- 项目编号必须符合规定格式
- 日期关系应满足工程流程顺序

## 5. 文件摄入和逐页提取

系统支持 PDF、扫描 PDF、Word、Excel、CSV、图片和 ZIP。原生文本和 OCR 统一进入页面级数据层，保存：

- `file_id`
- `page_no`
- `text`
- `fragments`
- `bbox`
- `table_id`
- `row_index`
- `column_index`
- `source`（原生文本、OCR 或多模态提取）

每一份文件从第一页查到最后一页，不能只读取前两页。同一个字段在同一份文件中出现多次时，全部保留。

字段候选必须能够在原始页面中定位，并保存页码和证据原文：

```json
{
  "field_key": "contract_amount",
  "value": "50000000",
  "page": 4,
  "evidence": "签约合同价：50000000元",
  "source": "native_pdf_text",
  "confidence": 0.99
}
```

字段类型校验、日期和金额归一化、候选去重由规则引擎完成；模型只负责提出 grounded 候选。

## 6. 生成 manifest.json

系统只从主参考文件提取并写入 manifest：

- 主参考文件有字段，写入值、页码和证据
- 主参考文件没有字段，保持空白
- 不使用其他文件补齐 manifest 空白
- 用户输入的项目名称作为任务身份保留

```json
{
  "project_type": "housing-construction",
  "project_name": "云港新区市民活动中心图书馆工程",
  "primary_reference": {
    "file_id": "file_001",
    "file_name": "建筑工程施工许可证.pdf",
    "document_code": "A-02"
  },
  "fields": {
    "project_code": {
      "value": "YG-SQ-TSG-2024-003",
      "page": 1,
      "evidence": "编号：YG-SQ-TSG-2024-003"
    },
    "contract_amount": {
      "value": null,
      "page": null,
      "evidence": null
    }
  }
}
```

## 7. 字段一致性核查

### 7.1 字段适用范围

字段只在规则指定的文件中查找。字段不适用于某类文件时，返回：

```json
{
  "applicable": false,
  "reason": "该字段不属于此类文件"
}
```

不适用不算缺失，也不参与比较。

### 7.2 manifest 有值时

将所有适用文件中的有值字段与 manifest 比较。所有有值内容一致，字段才通过；出现不同值则需要复核。

```text
manifest：50000000
施工合同：50000000
监理报告：不适用
竣工报告：52000000
结果：需复核
```

### 7.3 manifest 没有值时

不与空 manifest 比较，但如果至少两个适用文件有值，就互相比较：

- 只有一个文件有值：记录候选值，不判冲突
- 两个或以上文件有值且一致：字段通过
- 两个或以上文件有值但不一致：需人工复核

## 8. 中英文名称匹配

项目名称和单位名称支持：

```text
精确匹配
→ 空格、大小写和标点归一化
→ 中英文后缀映射
→ 双语别名匹配
→ 语义等价判断
→ 无法确认时人工复核
```

例如：

```text
东海建工集团有限公司
Donghai Construction Group Co., Ltd.
```

项目编号、合同编号、金额和日期必须采用严格比较，不能依赖模糊语义。

## 9. 材料完整性、归属和重复核查

系统根据 `required_documents` 检查必需资料是否存在，判断近似文件是否可以替代，并识别：

- 其他工程资料混入
- 文件编号或报告编号重复
- 内容指纹高度相似的重复件
- 不可读或损坏文件

错传文件不计入当前项目的材料已提供，也不参与本项目字段共识。

## 10. 四种统一状态

所有材料、字段和规则结果统一使用四种状态：

```text
provided
missing
suspect_duplicate_or_misfiled
needs_human_review
```

- `provided`：已找到且证据足够
- `missing`：必需资料或必需字段没有找到
- `suspect_duplicate_or_misfiled`：疑似重复或属于其他工程
- `needs_human_review`：存在冲突、证据不足、OCR 不清楚或无法判断

字段“不适用”是 `applicable=false`，不是上述四种状态之一。

## 11. 前端返回结构

前端需要支持每个文件预览，并显示该文件中提取出的全部字段。

```json
{
  "file_id": "file_001",
  "file_name": "施工合同.pdf",
  "preview": {
    "url": "/files/file_001/preview",
    "page_count": 18
  },
  "fields": [
    {
      "field_key": "project_name",
      "field_name": "项目名称",
      "value": "云港新区市民活动中心图书馆工程",
      "page": 1,
      "evidence": "工程名称：云港新区市民活动中心图书馆工程",
      "status": "provided",
      "applicable": true
    }
  ]
}
```

前端应支持：

- 每个文件逐页预览
- 查看文件中所有提取字段
- 点击字段跳转到对应页
- 高亮字段证据原文
- 展示字段状态、规则状态和置信度
- 区分“不适用”“没有提取到”和“字段冲突”

字段比较结果示例：

```json
{
  "field_key": "contract_amount",
  "field_name": "合同金额",
  "manifest_value": "50000000",
  "status": "needs_human_review",
  "values_by_file": [
    {
      "file_name": "施工合同.pdf",
      "value": "50000000",
      "page": 4,
      "status": "provided"
    },
    {
      "file_name": "监理报告.pdf",
      "value": null,
      "applicable": false
    },
    {
      "file_name": "施工单位竣工报告.pdf",
      "value": "52000000",
      "page": 2,
      "status": "needs_human_review"
    }
  ],
  "rule_ids": ["R-002"],
  "reason": "适用文件中存在两个不同合同金额"
}
```

规则结果单独返回，让前端显示规则名称和产生原因：

```json
{
  "rule_id": "R-002",
  "rule_name": "manifest 字段一致性",
  "status": "needs_human_review",
  "related_fields": ["contract_amount"],
  "related_files": ["施工合同.pdf", "施工单位竣工报告.pdf"],
  "reason": "50000000 与 52000000 不一致"
}
```

## 12. 输出文件

```text
output/
├── manifest.json
├── inventory.json
├── fields.json
├── field_consensus.json
├── evidence.json
├── findings.json
├── audit-report.md
├── audit-brief.md
└── run_stats.json
```

- `manifest.json`：主参考文件生成的结构化锚点
- `fields.json`：每个文件逐页提取的字段
- `field_consensus.json`：字段比较和共识结果
- `evidence.json`：页码、原文、坐标和来源
- `findings.json`：机器可读核查结论
- `audit-report.md`：人类可读报告
- `audit-brief.md`：给 AGH/Agent 复核的精简摘要
- `run_stats.json`：页数、OCR、模型调用、耗时和 Token 统计

## 13. AGH 中的职责划分

```text
规则文件：定义字段、文件范围和核查规则
确定性代码：逐页提取、类型校验、归一化和规则计算
AGH/Agent：读取 Skill、调用工具、复核疑点和整理报告
前端：预览文件、展示字段、展示规则和证据
```

最终系统以 `manifest.json` 为结构化锚点，以规则文件为唯一字段和规则来源，以逐页证据链为核查依据，并向前端同时返回文件级字段结果和规则级核查结果。
